# 实现需求文档

## 触发场景

用户提出以下类似指令时启用本技能：
- "实现一下需求"
- "把待实现的需求做了"
- "看下 requirements/todo 里的需求"

## 执行流程

```
Task Progress:
- [ ] Task 1: 扫描待实现需求目录
- [ ] Task 2: 读取并解析需求文档
- [ ] Task 3: 确认实现范围
- [ ] Task 4: 定位并实现代码
- [ ] Task 5: 构建验证
- [ ] Task 6: 归档需求文档
```

---

## Task 1: 扫描待实现需求

```bash
ls requirements/todo/
```

- **有且仅有一个需求文档** → 直接进入 Task 2
- **有多个** → 列出清单询问用户实现哪一个
- **目录为空** → 告知用户无待实现需求，终止流程

---

## Task 2: 读取并解析需求文档

完整读取需求文档（`.md` 文件），提取以下关键信息：

| 提取项 | 说明 |
|--------|------|
| 功能概述 | 这个需求要解决什么问题 |
| 数据模型 | 涉及哪些数据结构、配置项 |
| 逻辑处理 | 需要哪些业务逻辑、接口、后台服务 |
| 界面/交互 | 有哪些页面、窗口、操作交互 |
| 边界条件 | 特殊规则、校验逻辑、异常处理 |

**如果需求文档描述模糊或存在歧义，必须先向用户澄清，不要凭空假设。**

---

## Task 3: 确认实现范围

向用户简要复述理解的需求要点，并说明打算怎么做。
除非用户明确要求先确认，否则**说明后直接开始实现，不要停下来等待批准**。

---

## Task 4: 定位并实现代码

### 先了解项目本身

不同项目技术栈和分层不同，动手前先快速摸清当前项目的结构：
- 看 README / Makefile / 目录结构，确定技术栈与分层方式
- 找到与需求最相似的已有功能，作为参照物

### 判断需求类型

- **全新功能模块** → 按项目现有分层从零搭建
- **在已有模块上增改** → 定位相关文件后做针对性修改

### 通用实现规则（所有项目一致）

- **向现有代码看齐**：命名、目录位置、分层结构、框架用法都参照项目内已有写法，不引入新框架、新依赖（除非需求明确要求）
- **架构纪律**：业务逻辑写在项目规定的逻辑层（服务层 / ViewModel 等），不堆在展示层
- **注释规范**：每个新文件、类、公开方法、复杂逻辑都加中文注释
- **配置兼容**：修改配置结构时同步更新默认值与迁移逻辑，避免旧配置加载失败

---

## Task 5: 构建验证

使用**项目自身的构建方式**编译验证。不确定就查 Makefile / README / package.json / .sln。

常见示例：
```bash
go build ./...            # Go 项目
dotnet build Xxx.sln      # .NET 项目
npm run build             # 前端项目
```

**必须零报错才算完成。** 有错误则修复后重新验证，循环直到通过。

---

## Task 6: 归档需求文档

构建验证通过后，将需求文档从 `requirements/todo/` 移动到 `requirements/done/`：

```bash
git mv "requirements/todo/<需求文档>.md" "requirements/done/"
```

（文件尚未纳入 git 时直接用普通移动即可）

---

## 完成后的输出

向用户汇报：
1. 实现了哪些文件（按项目分层列出）
2. 核心逻辑的处理方式
3. 构建验证结果
4. 需求文档已归档到 `requirements/done/`
5. 提示可以使用 `/push-release` 指令进行版本发布
